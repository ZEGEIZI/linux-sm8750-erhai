# Guidance for coding agents

A downstream Linux tree for the OnePlus Pad 2 Pro (`erhai`, SM8750). For AI agents working here on behalf of a contributor. [.github/CONTRIBUTING.md](.github/CONTRIBUTING.md) is the authority; commits, the DCO and attribution follow the target kernel's `Documentation/process/submitting-patches.rst` and `coding-assistants.rst`.

- **Target and scope.** Target `erhai/v0.7` (the current release line); fetch it from this project's repository (your `origin` may be a fork), rebase onto it and review the complete final diff; never base a PR on an older release line. Configuration fragments live here under `arch/arm64/configs/`; the integration repository's `kernel/source.json` lists which ones a release uses. Device packages, userspace and build tools live in [onepluspad-2pro-mainline](https://github.com/yzddmr6/onepluspad-2pro-mainline); open a companion PR there and state the merge order.
- **One topic per PR.** Each commit is one logical change that builds on its own; split bindings, drivers and board enablement. Do not bundle unrelated features.
- **Read before you write.** Follow the real call path and every existing consumer. When you add a device-tree child node, check every driver that walks that parent's children. Fixed reserved-memory addresses must lie inside RAM on both 12 GB and 16 GB units. Hardware parameters need a stock or upstream reference.
- **Build as releases are built.** Use the fragments listed in `kernel/source.json`; check that the options you need are really set in the final `.config` (unmet dependencies are dropped silently); no new warnings; run checkpatch on your series and `dt_binding_check`/`dtbs_check` for changed bindings or DTS. Probe failure, remove and power-state paths must release what they took.
- **Make claims checkable.** Feature and fix statements must match the final diff and the real call path; test statements name the build, scenario and result; after a rebase, say which evidence still applies. Check error paths by source review or offline fault injection, not by unbinding drivers of hardware in use.
- **Device tests are the contributor's.** Ask them to run CONTRIBUTING item 6 and paste sanitised results; never report a test you did not see run. Do not flash, wipe or reboot a device unless the contributor explicitly asks, and only the device they named.
- **Attribution.** Never add `Signed-off-by:` (the human contributor certifies the DCO), `Tested-by:` or `Reviewed-by:` for anyone. Add a trailer naming the model that actually did the work, `Co-Authored-By: <model> <email>` (for example `Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>`) or the `Assisted-by: <agent>:<model version>` format of the kernel 7.2 `coding-assistants.rst`, one per model; if you do not know your exact model, ask the contributor rather than guess. State the tools and models in the PR; never paste prompts, session logs or private task notes into commits or PRs. Keep the author, date, trailers and `Link:` of imported patches; put local changes in separate commits.
- **Hard limits.** Do not change the integration repository's version locks or release inputs. Do not print serial numbers, device addresses or calibration at default log levels, and keep personal data out of commits.
